## Part1-MySQL

学习资源：https://www.runoob.com/mysql/mysql-tutorial.html
				     https://www.mysqltutorial.org/

在软件开发过程中，数据是系统运行的重要基础。

例如，一个校园系统需要保存学生信息，一个论坛需要保存用户和帖子，一个商城需要保存商品和订单。随着系统规模扩大，单纯使用文件保存数据会逐渐暴露出问题：

- 数据查询效率低；
- 数据结构难以维护；
- 多人同时操作时容易出现数据不一致。

因此，实际项目中通常会使用数据库来存储和管理数据。

MySQL 是目前应用较广泛的关系型数据库之一。它使用数据表组织信息，并通过 SQL 语句完成数据的增删改查。

例如，一个学生信息表可能包含：

```mysql
students

id      name      age

2       李四       1
```

其中每一行代表一条记录，每一列代表数据的一个属性。

## Part2-Docker

学习资源：https://www.runoob.com/docker/docker-tutorial.html
				  https://docs.docker.com/get-started/
				  https://www.itbaima.cn/en-US/document/zj9uvg0sp3b0sok8

不知道你有没有遇到过这种情况：你在自己电脑上写了个 Java 程序，跑得好好的，发给别人就跑不起来了—种种问题类似："我这是 Mac 系统跟你不一样"、"我 JDK 版本跟你不一样"、"我 Windows 路径写法跟你 Linux 不一样"。这就是环境不一致带来的问题。

Docker 技术就是为了解决这个而生的。它把你的程序和它需要的一切环境（JDK、配置文件、依赖）打包到一个叫"镜像"的东西里，只要 CPU 架构相同，拿到任何装了 Docker 的机器上都能直接运行。

你可能想问：那跟我用虚拟机有啥区别？虚拟机是在你的系统里完整模拟一台电脑，包括它的整个操作系统，占几个 G 的内存，启动要好几分钟。Docker 共享宿主机的 **Linux 内核**，不需要在容器内自带独立的 **内核**，因而极其轻量。你后面调试项目的时候动不动就要重启容器，如果用虚拟机，等开机都能等到你崩溃。

下面是几个基础但重要的概念：

import { Badge } from '@astrojs/starlight/components';

**镜像（Image）**：一个只读的模板，里面装好了操作系统、软件、代码、配置，是"静止的"。比如 <Badge text="mysql:8.0" /> 这个镜像，里面包含运行 MySQL 8.0 所需的最小化运行依赖、动态库和配置文件。

**容器（Container）**：镜像跑起来之后的运行实例，是"活动的"。同一个镜像可以启动多个容器，互相隔离，谁也看不到谁的数据。用面向对象的说法来类比：镜像 = 类，容器 = 对象。

**Dockerfile**：一个文本文件，告诉 Docker 怎么一步一步构建你的镜像。比如：
```
FROM openjdk:17
COPY target/app.jar app.jar
CMD ["java", "-jar", "app.jar"]
```
基于 openjdk:17 基础镜像，把编译好的 jar 包复制进去，并指定默认启动命令。像 RUN、COPY 这类指令会产生单独的镜像层，Docker 构建时会严格按顺序对比每一层的缓存。只要某一层（比如复制代码）内容变了，它以及它后面的所有指令层都必须重新构建。所以构建优化的一条铁律是：把很少变动的指令（如安装系统依赖）写在前面，把频繁变动的指令（如复制代码）写在后面。

docker-compose.yml：当你的项目需要同时运行 MySQL、Java 后端、Nginx 多个容器时，手动敲 docker run 挂载参数不仅效率低且极易出错。Docker Compose 让你在一个 YAML 文件里集中定义所有容器的配置：镜像来源、端口映射、环境变量以及容器依赖关系（depends_on）。配置完成后，只需一条 docker compose up -d 就能按顺序启动整套服务架构。

**最容易出问题的地方—网络** 

每个容器内部都是独立的网络隔离空间，都有自己的 localhost。如果你在 Java 容器的代码里把数据库连接地址写成 localhost:3306，Java 会去连接自己容器内的 3306 端口，而 MySQL 运行在另一个独立的容器里，导致连接直接失败。 在 Docker Compose 中，默认会为当前配置下的所有容器创建一个共享的虚拟网络。容器之间不再依靠 IP 通信，而是直接通过服务名（service name）进行 DNS 解析。如果你的 MySQL 服务名定义为 mysql，那么 Java 的数据库连接地址必须写成：

```
jdbc:mysql://mysql:3306/board
```

这里的 <Badge text="mysql" /> 就是 docker-compose.yml 里 MySQL 服务的名字。不是 <Badge text="localhost" />，也不是 IP 地址。很多新手第一次都会在这里卡住，把 <Badge text="localhost" /> 改成服务名就好了。

---

可能会遇到的问题：

- **启动顺序问题**：MySQL 容器启动之后，MySQL 服务本身还需要几秒才能开始接受连接（它要初始化数据、建表）。Java 后端启动很快，可能 MySQL 还没就绪它就开始尝试连接了，这时候会报 <Badge text="Connection refused" />。解决方法是给 MySQL 加健康检查（healthcheck），然后在 Java 的 <Badge text="depends_on" /> 里配置 <Badge text="condition: service_healthy" />，让 Docker 等 MySQL 健康了再启动 Java。

- **路径问题**：Dockerfile 里的 <Badge text="COPY" />、compose 文件里的 <Badge text="volumes" />，路径都是相对于当前文件所在目录的。比如在 docker-compose.yml 里写 <Badge text="./nginx/nginx.conf:/etc/nginx/nginx.conf" />，前面的路径相对于 docker-compose.yml。写错了就会报 <Badge text="no such file or directory" />。看到这个报错先检查路径。

---

**常用命令**（仅举例）

```
docker compose up -d              # 启动所有容器（-d 后台运行）
docker compose down               # 停掉所有容器
docker compose build --no-cache   # 重新构建镜像
docker compose logs <服务名>      # 看日志——排查第一工具
docker ps -a                      # 看所有容器的运行状态
docker exec -it <容器名> sh       # 进入容器内部
```

## Part3-Nginx

学习资源：https://nginx.org/cn/docs/
				  https://github.com/dunwu/nginx-tutorial

**为什么需要 Nginx？**

在刚开始学习 Web 开发时，一个项目可能只有一个服务器：

```
用户
 ↓
后端服务器
```

所有请求都直接发送给后端程序，看起来非常简单。

但是随着用户数量增加，一个服务器可能会逐渐承担越来越大的压力。例如同时有大量用户访问网站，服务器可能出现响应变慢甚至无法访问的情况。这个时候，单独依靠一台服务器已经难以满足需求。

一种常见的解决方式是增加服务器数量，让多个后端程序一起工作：

```
          后端服务器1
        /
用户 → Nginx → 后端服务器2
        \
          后端服务器3
```

但是新的问题又出现了：用户并不知道应该访问哪一台服务器，也不应该由用户自己决定请求发送到哪里。这时就需要一个中间角色来帮助管理请求。

Nginx 就承担了这个角色。

它可以接收用户请求，根据配置将请求转发给不同的后端服务器，这个过程叫做**反向代理**。同时，Nginx 还可以根据服务器当前压力分配请求，让多个服务器共同承担访问压力，这就是**负载均衡**。

除了转发请求，Nginx 还可以处理静态资源，例如网页中的图片、CSS、JavaScript 文件等。相比让后端程序处理这些简单文件，Nginx 可以更加高效地完成这些工作。

简单来说：

> 用户只需要访问 Nginx，而 Nginx 负责管理后面的服务器。它就像网站的“前台接待”，先接收所有访问请求，再根据情况安排给合适的后端服务。

Nginx 的配置写在 nginx.conf 里，核心结构如下：

```
server {
    listen 80;

    location / {
        root /usr/share/nginx/html;
    }

    location /api/ {
        proxy_pass http://backend:8080;
    }
}
```

<Badge text="server" /> 块定义一个虚拟服务器。<Badge text="listen 80" /> 表示监听 80 端口。

<Badge text="location" /> 块按路径匹配请求。<Badge text="location /" /> 匹配所有请求，<Badge text="location /api/" /> 只匹配以 <Badge text="/api/" /> 开头的请求。Nginx 的匹配规则是**最长匹配前缀优先**——<Badge text="/api/messages" /> 会命中 <Badge text="/api/" /> 而不是 <Badge text="/" />，因为 <Badge text="/api/" /> 更精确。

<Badge text="proxy_pass" /> 是反向代理的核心指令。<Badge text="http://backend:8080" /> 告诉 Nginx 把请求转发到这个地址。这里的 <Badge text="backend" /> 是 docker-compose.yml 里 Java 后端的服务名——还记得 Docker 里的"容器间用服务名通信"吗？

## Part4-HTTP

你在浏览网页时，可能会发现一个现象：

当你打开一个网站、点击登录按钮、提交评论时，浏览器并不是直接“打开”服务器上的内容，而是向服务器发送一条请求，服务器处理后再返回结果。

那么，浏览器和服务器之间到底是如何交流的？

HTTP（HyperText Transfer Protocol）就是它们之间沟通的规则。一次 HTTP 请求中包含了请求方法、请求地址、Header、请求体等信息，服务器会根据这些内容判断客户端想做什么。

例如：

你访问一个网页：

```
GET /index.html
```

import p_7_2 from '../../../assets/backend/7-2.png';

<Image src={p_7_2} alt="7-2" />

实际上是在告诉服务器：

> 请把 index.html 的内容返回给我。

而当你登录一个网站时：

```
POST /login
```

则是在告诉服务器：

> 我有一些数据需要提交给你，请帮我处理。

在这个过程中，你会遇到各种不同的 HTTP 状态码，它们用于表示服务器对请求的处理结果。比如：

### Task3：发送 POST 请求提交数据

前面的任务中，我们主要通过 HTTP 请求**获取数据**。

但是在实际开发中，很多操作都需要向服务器提交数据，例如：

- 用户注册提交账号密码
- 用户登录提交身份信息
- 发布文章提交文章内容
- 上传表单提交用户信息

这些场景通常使用 **POST 请求**。

现在请使用 **Postman** 向以下地址发送 POST 请求：
